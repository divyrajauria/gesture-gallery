Designing a hand-gesture-based photo gallery

A photo grid controlled by a webcam and four hand poses. Google's MediaPipe Hands returns 21 landmarks per frame. Everything downstream is custom: pose classification, cursor smoothing, a depth proxy for zoom, input-gated onboarding and a full keyboard fallback.

02

What I noticed

Every precondition is a drop-off point.

Most hand-tracking demos assume a webcam, a well-lit room, and someone who already knows the moves. The person I was designing for has none of that guaranteed. They open the link between other tabs, their browser blocks the camera, and nobody has told them what a grab looks like.

Each of those assumptions is a gate, and every gate is a place to lose someone. So I listed the gates first, and gave each one a fix before adding anything new.

03

Reading the hand

Pose classification from landmark geometry, with one guard against false grabs.

MediaPipe Hands returns 21 landmarks per frame. The rest is mine. Each finger is classed as extended or curled by comparing its tip with its middle (PIP) joint, which yields open palm, point and fist. A new pose must persist for 90 ms before it takes over, so the mode never flickers. The cursor runs through a One-Euro filter: heavy smoothing when the hand is still, low lag when it moves. A tap is a fingertip dip, normalised to hand size, inside a 220 ms window, so slow drift never selects.

The obvious grab is a pinch. But a hand closing into a fist passes through a pinch on the way, so a plain pinch threshold fires whenever someone starts to scroll. The grab is an OK sign instead: thumb-to-index distance under 0.55 of hand size, with the other three fingers extended, evaluated on the raw per-frame pose rather than the smoothed one. It's harder to discover. I accepted that trade, because a false grab costs more than a gesture that takes a few seconds to learn.

Depth without a depth sensor

A webcam gives no usable z-axis, but apparent hand size falls with distance. So zoom is driven by hand size: as the hand shrinks in frame, the photo scales up through a smoothed gain. Lateral movement maps to drag, so the two axes never conflict.

04

Teaching it

Onboarding gated on detected input, not on clicks.

A first-run tour teaches one gesture per step and advances only when the classifier sees it performed, because doing a gesture teaches more than reading about it. Back and Next allow revisiting, and the guide can replay the tour at any time.

My first version taught the wrong gesture: the copy said "pinch, then pull back towards you" while the classifier expected an OK sign moved away from the screen. The simulated tests passed; my own hand caught it. Loosening detection would have brought the false grabs back, so the fix was copy that matches the classifier exactly, plus live hints computed from the current pose.

The gesture you teach has to be the gesture the code checks for.

05

When the camera says no

Graceful degradation: every gesture has a keyboard and pointer equivalent.

The first build blocked on a full-screen spinner until tracking loaded; with the camera denied, it blocked forever. Now the grid is interactive on first paint, the model loads in the background, and a status card reports state.

Each getUserMedia failure (NotAllowedError, NotFoundError, NotReadableError) maps to its own message and recovery path. The camera helper library surfaced raw browser alerts, so I call getUserMedia directly.

The grid is an ARIA multi-select listbox with a roving tabindex, so it's a single Tab stop. Arrows move, Space toggles, Enter enlarges, Esc closes, and selection changes go to a live region. prefers-reduced-motion removes decorative motion but keeps hand-driven movement, because here movement is the interface.

06

Selection that goes somewhere

One input primitive for content and controls.

Selection used to dead-end at "3 Selected". It now raises a Remove and Clear bar, and every removal gets an Undo. Removal is soft (tiles are hidden, not deleted), so it's safe to try.

No new gesture: the tap dispatches to whatever control is under the cursor, with a hover state when the hand is over it. Targets are 36 px tall to absorb cursor jitter, and the header reserves the bar's space, so the grid never shifts when it appears.

07

Light on the machine

Frame budget: give the model the headroom.

At 30 fps each frame has 33 ms, and inference takes a large share of it. I profiled the page's own cost under 4× CPU throttling, as a proxy for an average laptop. Idle, it was spending about 14 ms per frame on nothing.

Four causes, none visible. A hidden spinner kept animating and forced a repaint every frame. All 200 tiles were layer-promoted with will-change, so each repaint touched every layer. Hover hit-testing measured every tile instead of one elementFromPoint call. And inference ran on every requestAnimationFrame (about 60 Hz) though the webcam delivers about 30 fps.

On visibilitychange the camera track is stopped, so the hardware light goes off, and it reconnects on return. I verified that in a headed browser, because headless test runs never report a page as hidden.

Idle should cost nothing. Most of the fixes were deleting work.

08

Proving it without a webcam

59 deterministic end-to-end tests, driven by synthetic landmarks.

CI has no webcam. The tests replace the MediaPipe script with a stub and inject 21-landmark hands frame by frame at webcam cadence, so the page's real gesture code runs unmodified. Coverage: every gesture, keyboard and mouse, each camera failure, the tour and its hints, Remove and Undo, the offline photo fallback and reduced motion.

To prove the suite catches regressions, I broke the OK-sign rule on purpose; the matching test failed immediately. GitHub Actions runs the suite on every pull request, so a broken gesture can't reach the live site unnoticed.

09

How I worked

I set the direction, an AI pair wrote much of the code, and my own hand was the final test.

One change per branch: proposed, implemented, run against the suite, then tried on my own camera before merging to main, which deploys to GitHub Pages. The simulations caught most problems. My hand caught the one they couldn't: a tour teaching a different gesture from the one the code checked for.

Scope came from the one-minute test. A calibration indicator ("too close, too far") was on the list, and I dropped it, because the tour's live hints already cover the main confusion. Mobile support and new gestures stayed out for the same reason: neither changes how someone skimming judges the piece.

11

What I'd change, and what's next

The performance numbers come from a slowed-down browser, not a real mid-range laptop, and they leave out the model's own cost. That's the next thing I'd measure, on borrowed hardware, before calling it fast.

I'd also bring in other people's hands earlier. Every gesture threshold was tuned on mine, so the next round is a few people, a few lighting conditions, and a few minutes each, watching where the hints fire.
